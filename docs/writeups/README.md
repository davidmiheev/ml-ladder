# Writeups

One document per part, written when the part's rungs are finished. The part
README (`parts/<package>/README.md`) is the short version — what the rungs are
and what the runs show; the writeup here is the long version — why each design
decision, what the numbers say across seeds, what was surprising, and what is
left open.

## The structure

Every writeup follows the same shape, because the shape is what makes them
comparable across parts:

1. **Header block** — status, the constraint the part works under, which seeds
   the numbers come from, and the command that reproduces them.
2. **Through-line** — the one idea that ties the part's rungs together. Written
   last, but it is the part worth reading.
3. **One section per rung**, each with: *Question* (what the rung is actually
   asking), **The math** (the objective, its gradient or optimality condition,
   and the property that explains what you measured), *What I built* (design
   decisions and the non-obvious details), *Results* (a table with per-seed
   ranges, plus figures), *What surprised me*, *Open threads*, and *Reading* —
   the entries from [the reading list](../reading-list.md) that belong with the
   rung.
4. **What the part settled** — the numbered takeaways, including the ones that
   are about method rather than about the algorithms.

## The rules that keep them honest

- **Every headline number carries a range across seeds**, not a single run.
  Part A's writeup exists in its current form because a seed-0 number said
  XGBoost beat the from-scratch booster by 2%, and three seeds said the gap has
  no sign.
- **Numbers come from `data/<part>-metrics.json`**, regenerated by the tool, not
  transcribed from a terminal by hand.
- **Figures come from the reference seed** and live in `figures/<part>/`.
- **Surprises are recorded, including the wrong turns.** A writeup with no
  retractions in it is usually a writeup that stopped looking.
- **The math comes before the results, and is derived rather than cited.** The
  point is not to decorate the document with formulas — it is that the
  derivation should *predict* the measurement, and the measurement should audit
  the derivation. Part A's three examples: the SGD variance floor predicts an
  $|B|^{-1/2}$ scaling and the fit gives $-0.54$; the k-means/PCA constraint-set
  argument forces $E_{\text{k-means}}(k) \ge E_{\text{PCA}}(k-1)$ and it holds at
  every $k$; XGBoost's Newton leaf weight collapses to the mean residual at
  $\lambda = 0$, so the two boosters must agree — and they do, to $6\times10^{-6}$.
  Where a derivation makes a checkable claim, it becomes a test.
- **Math renders with GitHub's MathJax:** `$inline$` and `$$display$$` blocks,
  the latter surrounded by blank lines.

## Regenerating

```sh
uv run python tools/writeup_figures.py A            # figures + metrics, seeds 0-2
uv run python tools/writeup_figures.py A --seeds 0 1 2 3 4
uv run python tools/writeup_figures.py A --check    # fail if the committed metrics drifted
                                                    # (wall-clock metrics excluded — they vary per run)
                                                    # run it on the device the metrics came from: the
                                                    # same seed gives different numbers on CPU and GPU
make writeups                                        # every complete part
```

Each rung is run once per seed into a scratch directory; the reference seed's
figures are copied to `figures/<part>/` and every run's metrics are collected
into `data/<part>-metrics.json`.

## PDFs

Each finished writeup is also committed as a PDF, typeset through LaTeX so the
derivations set properly and the figures become numbered floats with captions:

```sh
make pdf-A                                  # docs/writeups/pdf/a-classical.pdf
make pdf                                    # every finished part
uv run python tools/build_pdf.py A --keep   # also keep the intermediate .tex
```

The pipeline is markdown → LaTeX (pandoc) → PDF (XeLaTeX), which needs
`pandoc texlive-xetex texlive-latex-extra texlive-fonts-recommended` installed;
readers need none of it, since the PDF is in the repo. The build fails rather
than silently dropping glyphs: XeTeX reports unmapped characters as *Missing
character* log lines, and `tools/build_pdf.py` turns those into an error — so
if a writeup introduces a symbol the font lacks, the build says so instead of
shipping a PDF with a hole in it. Prefer real math (`$\ge$`) over the bare
unicode character in prose for the same reason.

## The check

`tests/test_writeups.py` asserts that every part has a writeup, that a part
whose rungs are all implemented has a *finished* one (no `TODO(writeup)`
markers, a `**Status:** complete` header, a section per rung), and that every
figure a writeup references actually exists. A finished part with an unfinished
writeup fails CI — which is the point.
